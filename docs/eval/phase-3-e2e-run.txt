teardown doubles as US-6 erasure evidence.

======================================================================

Against a dev server started with a deliberately invalid model key, so every
OpenRouter call fails for real:

    OPENROUTER_API_KEY=<invalid> npx next dev -p 3100
    E2E_AI_DOWN=1 E2E_BASE_URL=http://localhost:3100 npx playwright test scan -g "AI failure"

Same branch, same commit, same clean tree. Next 16 allows one dev server per
directory, so the port-3000 server above was stopped first (by its own PID -
CLAUDE.md, Process).

What the case asserts, and therefore what this run proves:
  - POST /api/scan answers 502 with code AI_UNAVAILABLE and the message
    "AI service is unavailable. Your vacancy was saved - retry from
    Applications." - the endpoint-specific string, which is true here because
    the vacancy and a draft application are written BEFORE the model call;
  - that message appears as a toast and NOT inline (Block E's error state for
    this screen is a toast);
  - the row exists on /applications as a draft, with no score ("-") and the
    Position cell reading "Not analysed yet";
  - the detail screen shows "This scan has not been analysed yet" plus
    [Run analysis] - never an empty coverage table, which would read as
    "no gaps found";
  - pressing [Run analysis] posts { applicationId } and nothing else, spends one
    request, and gets the same honest 502 back rather than a spinner or a silent
    retry ladder.

RUN 3 - the coverage probe, twice (the calibration's own evidence)
======================================================================

Not part of the Playwright suite: `node scripts/coverage-probe.mjs --seed
docs/eval/calibration-case.json`, once before the recalibration and once after,
each against a throwaway account it created and then deleted. The labeled set,
the distribution, the derived thresholds and the cost of the split are in
docs/eval/coverage-thresholds.md. Two results from those runs belong here
because they are evidence about the app rather than about the thresholds:

  - The calibrated constants produce the predicted score IN THE APP: 17 before,
    57 after, with five of seven requirements covered - the four labeled-covered
    plus the single over-claim the calibration note declared in advance.

  - Embedding calls DO write llm_calls rows (rule B8), which the owner's own
    query could not see. Both runs reported, from the probe's own reading of the
    llm_calls DAL under RLS:

        embed            rows=2 with_application_id=0 cost_usd_micro=8
        parse_vacancy    rows=1 with_application_id=1 cost_usd_micro=2602
        import_resume    rows=1 with_application_id=0 cost_usd_micro=3545

    Two embed rows per run (one batch for indexing the base, one for the scan's
    requirements), ok=true, model text-embedding-3-small, a real cost. They
    carry application_id NULL by design, which is exactly why a query filtered
    on an application id finds the parse_vacancy row and none of the embedding
    rows. Backlog p3-8 threads an application id through the scan's embedding
    calls; the logging itself is not broken.

  - The keywords P1 returned on both runs were literal spans of the posting -
    8 keywords, keywordsDropped 0 - so the prompt half of the B1a fix held on
    this case. The server guard is the fence for when it does not, and it is
    unit-tested rather than waiting on a model to misbehave.
