WHAT THE 200 MEANT - the useful part of this round, recorded because the first
version of the test failed and the failure looked much worse than it was.

The new test first asserted `toBe(404)` on user B's GET of the detail page. It
got 200, with B signed in and sitting on A's application URL. Read at face
value that is a cross-user data leak, and it was investigated as one before
anything else was touched. It is not. Measured, in order:

  - user B's POST to /api/applications/<A id>/generate answers 404 NOT_FOUND
  - user B's PATCH to /api/applications/<A id>      answers 404 NOT_FOUND
  - user B's own /applications list contains 0 rows
  - a signed-in user requesting a uuid belonging to NOBODY also gets 200,
    while a genuinely unrouted path gets 404

The last line is the answer: Next.js returns 200 for `notFound()` in
DEVELOPMENT while rendering the not-found UI. RLS is doing its job on every
surface. The page assertion was testing the framework's dev behaviour, not this
app's authorization, and would have meant something different in production
than in CI.

So the test now asserts, for the read, the two things that are true in both
environments and are what actually matter: user B is shown the not-found page,
and no part of A's rendered heading reaches B's screen or B's list. The
unambiguous 404-not-403 assertions live on the two API calls, where the handler
owns the response and the status code is exactly what is being pinned.

THE OTHER TWO FAILURES IN THE FIRST RUN, and their cause, since they are a
consequence of this branch's own CSP work:

    x auth > client-side validation blocks submit on a malformed email
    x auth > client-side validation blocks submit on a too-short password

Both assert that a client-side validation failure costs NO round trip, by
failing if ANY POST is observed. The POST observed was

    http://localhost:3000/__nextjs_original-stack-frames

- Next's dev overlay symbolicating an error. The error was React's development
build calling eval(), which the new Content-Security-Policy did not permit:

    eval() is not supported in this environment. If this page was served with a
    `Content-Security-Policy` header, make sure that `unsafe-eval` is included.
    React requires eval() in development mode for various debugging features.

The validation itself was working perfectly the whole time. The fix is in
next.config.ts: `'unsafe-eval'` is added to script-src in DEVELOPMENT ONLY and
never in a deployed build, which production does not need - see
docs/eval/csp-verification.md, where five pages load clean under the production
policy. The alternative, switching the CSP off in development, would have meant
nobody exercised it until it broke in production, which is the failure the CSP
work set out to avoid.

THIS RUN CANNOT BE REPRODUCED AGAINST THIS SUPABASE PROJECT.

Registration was closed in the Supabase dashboard immediately after this run
(docs/deploy.md step 2), and it is what keeps strangers out of a deployment that
is reachable by anyone with the URL. All four specs create a throwaway account
by filling in the /signup form against that same project, so every spec that
needs an account now fails at its fixture rather than at its assertion. Nothing
in the application broke; the way the suite gets a user did.

Which cases that is: effectively all 34. auth.spec.ts signs up in almost every
case; career, generate and scan each build a fresh account per file, and
generate.spec.ts builds TWO (user A and user B) for the cross-user cases.

WHAT SOMEONE RE-RUNNING IT HAS TO DO FIRST. One of these, and neither is built:

  1. A second Supabase project for tests, with sign-ups open, its own URL and
     anon key in the test environment, and migrations 001-005 applied. The
     deployment's own project stays closed. This is the durable answer and it is
     the one to build if the suite is ever going to run more than once more.

  2. Pre-created accounts the specs sign INTO instead of registering. Cheaper to
     set up and it changes the specs: every signUp helper becomes a signIn, the
     fixtures stop being disposable, and each spec has to clean up after itself
     because the account survives the run. It also silently deletes coverage -
     auth.spec.ts's sign-up case and its duplicate-email case ARE the signup
     path, and there is nothing left to point them at.

  3. Re-opening registration on the live project for the length of a run. This
     is what was done for the erasure evidence (docs/eval/erasure-evidence.md),
     it works, and it is the option with a real cost: for that window the
     deployment's only gate is off, and the gate is the whole security model of
     a reachable Hobby deployment. Acceptable once, deliberately, with the
     window measured in minutes. Not a workflow.

WHAT THIS DOES NOT MEAN. It is not a regression and it does not expire this
file: this run tested the code at the commit it names, and that evidence stands.
What it means is that the NEXT change to a tested path has no green suite behind
it until one of the three options above exists. That is a real gap, not a
formality, and it is carried in docs/backlog.md under "Testing".
