    THE DELTA IS NOT ATTRIBUTABLE TO THE EDIT, and saying so is the point of
    writing it down. The two numbers measure different corpora: the stored one
    ranks the requirements against the CAREER BASE through match_documents over
    the whole index, the live one against the ~20 ephemeral units of a single
    resume. Rule B1's thresholds were calibrated in coverage-thresholds.md
    against the first corpus only. So some of the 8 points is the edit and some
    of it is the change of corpus, and this run recorded no re-score of the
    UNEDITED draft that would separate them. What the run does establish is that
    the endpoint measures the editor's text - every re-scored entry names no
    career item, and the similarities are not the stored ones re-served, both of
    which the spec asserts. Calibrating the second corpus is backlog p4-11.

    Across four runs of this case the live number came out 57%, 58%, 65% and 62%
    against the same stored 57% - including one that matched it exactly, two real
    measurements of different text rounding to the same integer. That is why the
    spec does not assert inequality: it would have failed on a day the app was
    right.

THE GROUNDING GATE, END TO END. The `judge` case submits a resume claiming a
Senior Staff Engineer role at Google, a team of 40, a PhD from Stanford and an
AWS certification, against a base of two annotation jobs at fictional companies.
Five violations, `grounding: fail`, verdict `revise` - and that verdict is
COMPUTED by lib/judge.ts from the report's own evidence, not read from the
model's `verdict` field. atsFormat scored 4 in the same report, which is the
point of rule B2 being a gate: a well-formatted invention is still an invention.

A DEFECT THIS SUITE FOUND IN ITS OWN BRANCH, before any reviewer did. The first
run of the whole path failed on the assertion that the draft must not name
Labelbox or Supervisely. It named both, in a SKILLS line reading "ms office,
google suite, labelbox, supervisely" - the vacancy's keyword list, pasted whole
into a resume grounded in a base that contains none of it. The cause was in this
branch's prompt assembly, not in the model alone: `parsedRequirementsJson`
carried `parsed.keywords`, and a tidy list of skill terms beside an instruction
to use the vacancy's exact spelling is an invitation to reproduce it. Block F's
template asks P2 for "Vacancy requirements"; the keyword list is out of the
WRITER'S prompt and stays in the REVIEWER'S, which is the party rule B4 is
enforced by (SPEC v2.16, endpoint #5 note 13). The assertion is permanent and has
passed on every run since.

ONE MORE OBSERVATION, recorded because it was seen once and is not reproducible.
That same first failing run emitted the literal token `NAME` as the resume's
first line - P2 rule 4's layout placeholder rather than a name - which would then
have become the export filename. It has not recurred, and the cause is real
whether or not it shows: the career base is a list of jobs and skills and carries
no name anywhere, so a grounded generator has nothing to put there. Refusing to
invent one is correct behaviour; the fix is to ASK for a name, and that is
backlog p4-7. The spec now logs a boolean for it on every run.
