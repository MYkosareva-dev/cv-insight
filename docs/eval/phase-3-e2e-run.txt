For the record of what the earlier runs found, and why they were themselves

module that owns it (commit fa9269d). That failure is kept in this note rather
than erased by a green run, because it is the most useful thing those runs
found: the suite now reads the threshold from lib/scoring, so this round's
chunking change - which moved similarities again - needed no test edit at all.

The scan cases spend real money: each imports a resume (one import_resume call)
and runs one scan (one parse_vacancy call plus the embedding requests). That is
the point - SPEC's US-2 acceptance is "Real LLM call happens server-side;
response visible to the user", and a mocked model cannot show it.

Note: the suite creates real accounts with unique throwaway addresses and
removes each one through the app's own deletion flow in afterEach, so the
teardown doubles as US-6 erasure evidence.

The last case is SKIPPED here and run separately below. The AI-unavailable path
needs a server whose model calls FAIL, and the OpenRouter call is server-side -
no browser script can make it fail. Skipping visibly, rather than passing while
unable to run, is why it is a test.skip on an env flag.

The "destination stream closed early" lines are a Next dev-mode artefact of a

RUN 2 - the AI-unavailable path (US-2 step 5, edge cases N2/N3/N5)
======================================================================

Against a dev server started with a deliberately invalid model key, so every
OpenRouter call fails for real:

    OPENROUTER_API_KEY=<invalid> npx next dev -p 3100
    E2E_AI_DOWN=1 E2E_BASE_URL=http://localhost:3100 npx playwright test scan -g "AI failure"

Same branch, same commit, same clean tree. Next 16 allows one dev server per
directory, so this ran after Playwright had torn down its own; the broken-key
server's PIDs were recorded at startup and it was stopped by them afterwards
(CLAUDE.md, Process - and see the Process section of docs/reviews/phase-3.md for
why that sentence is in this file).

What the case asserts, and therefore what this run proves:
  - POST /api/scan answers 502 with code AI_UNAVAILABLE and the message
    "AI service is unavailable. Your vacancy was saved - retry from
    Applications." - the endpoint-specific string, which is true here because
    the vacancy and a draft application are written BEFORE the model call;
  - that message appears as a toast and NOT inline (Block E's error state for
    this screen is a toast);
  - the row exists on /applications as a draft, with no score ("-") and the
    Position cell reading "Not analysed yet";
  - the detail screen shows "This scan has not been analysed yet" plus
    [Run analysis] - never an empty coverage table, which would read as
    "no gaps found";
  - pressing [Run analysis] posts { applicationId } and nothing else, spends one
    request, and gets the same honest 502 back rather than a spinner or a silent
    retry ladder.

RUN 3 - the coverage probe, before and after semantic chunking
======================================================================

Not part of the Playwright suite: `node scripts/coverage-probe.mjs --seed
<case> [--reindex]`, run five times across this round against throwaway
accounts it created and deleted. The labeled sets, both similarity
distributions, the derivation and the cost are in
docs/eval/coverage-thresholds.md - Part 1 (blob chunking) and Part 2 (semantic
chunking), kept side by side deliberately.

What those runs prove about the APP rather than about the thresholds:

  - THE CHUNKER RUNS AND THE RE-INDEX RUNS. The same five career items produce
    5 documents rows under the old chunker and 9 under the new one, and
    POST /api/dev/reindex reported the per-item swap (3 + 2 + 1 + 2 + 1), every
    item in state `reindexed`, 0 unindexed, 0 left on old rows. A mechanism that
    is configured is not a working one; this is the run in which it worked.

    RE-VERIFIED after the architect's fixes, because the fixes changed this
    exact code path: the same base now embeds its 9 chunks in ONE embedding
    request rather than five (one per item), which is what the batch packer was
    already there for, and every item reports its write state rather than a
    boolean that called an intact old index "0 rows".

  - CONCENTRATION IS FIXED, WHICH WAS THE DIAGNOSIS. Distinct chunks winning at
    least one requirement: 2 before, 4 after. Most requirements won by ONE
    chunk: 5 of 8 before, 3 of 8 after - and 2 counting only the requirements
    that actually matched, the third being a chunk "winning" a comparison at
    0.19 where nothing matched at all.

  - THE TWO NAMED-TOOL FALSE POSITIVES ARE NOT FIXED, and got stronger:
    "Proficient with MS Office or Google Suite" 0.4149 -> 0.4438 and
    "Experience with annotation tools such as Labelbox or Supervisely"
    0.4280 -> 0.4587, now the top two similarities of eight. Recorded here as
    well as in the eval note because it is the kind of result a green suite
    hides: every test passes, and two rows on the result screen are still
    wrong. Backlog p3-17 carries the mechanism that would fix it.

  - EMBEDDING COST OF A RE-INDEX, measured: 9 chunks, 1 embedding request,
    cost_usd_micro 9 for a five-item base. Embeddings are priced per token and
    chunking changes how text is divided, not how much of it there is.

  - THE LEXICAL GATE (v2.15) WAS MEASURED THE SAME WAY, three more seeded runs,
    recorded in docs/eval/coverage-thresholds.md Part 3. Both false positives
    are Gaps naming their missing term ("MS Office", "Labelbox"); all five
    `general` requirements kept the status they had; and the one tool
    requirement the base DOES satisfy (Python) stayed Covered - which is the
    difference between a gate that discriminates and one that distrusts tools.
    The classification for the eight requirements was 5 general / 3 tool /
    0 credential.

    The middle of those three runs exists because the first version of the P1
    edit narrowed the top-level keywords list from 10 terms to 5, halving K's
    denominator. Nothing failed; the number was simply wrong, and only a second
    run showed it. Recorded because "no test caught it" is the point.

    A FOURTH seeded run, after the architect pass, confirms the same eight rows
    with `terms` now filtered to literal spans of the vacancy: score 57, both
    tool requirements Gaps naming their term, Python still Covered, every
    `general` row unchanged. The filter dropped nothing on this case - P1 did
    return literal terms - which is what a fence looks like when the thing it
    guards against did not happen.
